## Контекст

Вопрос был консультационный — стоит ли делать для `apps/api` свой доменный слой и слой use-case. Изучение кода и `architecture.md` показало, что это была бы **дублёр того, что уже есть** в общих пакетах: use-case'ы (`GetProductsUseCase` и др.) уже живут в `packages/application`, а API по таблице зависимостей (`architecture.md`, строка 71) намеренно позиционирован как **тонкий persistence/HTTP-адаптер** (`domain` — только типы, `application`/`infrastructure` запрещены).

Решено: **слои не дублировать**, а закрыть конкретные пробелы в обработке ошибок.

## Проблемы, которые чиним

В `apps/api/src`:
1. Нет глобального `setErrorHandler` (`server.ts`) → `ZodError` от `.parse()` в `routes/products.ts:88,101,110,117` сейчас отдаёт **500 вместо 422**.
2. 404 формируется вручную и дублируется (`products.ts:103-104` и `119-120`).
3. Ответы об ошибках не имеют единого формата.

## Решение — локальная HTTP-модель ошибок

**Почему не `AppError` из domain:** правило `api → domain "types only"` (`architecture.md` строка 71). `instanceof` требует value-import, что нарушило бы правило. Локальная иерархия сохраняет правило, самодостаточна и тестируема.

## План изменений

### 1. Новый файл `apps/api/src/errors.ts`

Локальная мини-иерархия (один файл, по образцу `packages/domain/src/errors.ts`):

- `HttpError extends Error` — базовый класс: `abstract statusCode: number`, `code: string`, конструктор `(message, cause?)`, `this.name = this.constructor.name`.
- `NotFoundError extends HttpError` → `statusCode = 404`, `code = 'NotFoundError'`. Конструктор `(resource: string, id?: string)` → сообщение вида `Product not found` (или `Product "<id>" not found`).
- `ValidationError extends HttpError` → `422`, `code = 'ValidationError'`.
- `AuthError extends HttpError` → `401`, `code = 'AuthError'`.
- `PermissionError extends HttpError` → `403`, `code = 'PermissionError'`.
- `ConflictError extends HttpError` → `409`, `code = 'ConflictError'`.

(Заготовки под будущие use-case'ы; сейчас используется только `NotFoundError`.)

### 2. Глобальный обработчик в `apps/api/src/server.ts`

В `buildServer()`, сразу после `const fastify = Fastify(...)` и **до** регистраций плагинов — `fastify.setErrorHandler(...)`:

- `ZodError` (из `zod`) → **422**, тело `{ statusCode, error: 'ValidationError', message: 'Invalid request input', details: error.issues }`.
- `HttpError` → `error.statusCode`, тело `{ statusCode, error: code, message }`.
- всё остальное → логировать полный error через `request.log.error(error)`, отдать **500** `{ statusCode: 500, error: 'InternalServerError', message: 'Internal server error' }` (без утечки внутренностей).

Опционально `setNotFoundHandler` для единого формата неизвестных роутов (`{ statusCode: 404, error: 'NotFoundError', message: 'Route not found' }`).

### 3. Чистка `apps/api/src/routes/products.ts`

- Убрать ручной `reply.code(404).send({ error: 'Product not found' })` в `getById` (`:103-104`) и `update` (`:119-120`) → заменить на `throw new NotFoundError('Product', id)` из нового `../errors`. Контракт порта `IProductsRepository` (возвращает `IProduct | null`) **не трогаем** — маршрут сам решает, что `null` = не найдено.
- Импорт: `import { NotFoundError } from '../errors'`.
- `.parse(...)` оставляем как есть — выброшенный `ZodError` ловится глобальным обработчиком.

## Что НЕ входит в scope

- Domain/use-case слои в API (так и не делаем — обосновано выше).
- PATCH для exemplars (был второй опцией, не выбран).
- Изменение контракта порта `IProductsRepository`.
- Любые правки в общих пакетах.

## Проверка

- `cd apps/api && npx tsc --noEmit` — типы.
- Ручной прогон `dev:api` (опционально): невалидный JSON в POST → 422 с `details`; `GET /products/<несуществующий-uuid>` → 404 в едином формате; `GET /products/не-uuid` → 422.
