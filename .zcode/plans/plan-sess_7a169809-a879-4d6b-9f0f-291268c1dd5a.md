# План: перенос всех use case в composition root

## Контекст (верифицировано, не догадки)

В приложении 3 use case. Сейчас wiring размазан:
- `GetCurrentUserUseCase`, `ToggleFavoriteProductUseCase` — создаются в хуке `use-favorites.ts` внутри локального `createIsomorphicFn`.
- `GetProductsUseCase` — создаётся внутри handler-а `products.functions.ts`.

Цель: **все** use case создаются в composition root; хуки и server-fn потребляют готовые экземпляры.

Агенты-исследования подтвердили два ключевых факта:
1. `createIsomorphicFn().server(s).client(c)` — порядок вызовов **неважен** (для типов, рантайма и трансформации плагином). Мои прошлые ошибки с `tsc` были из неверных аннотаций типа, не из порядка.
2. **Нет taint на экспортированных именах.** Если `index.client.ts` экспортирует use case, обёрнутый в `createIsomorphicFn().client(...)`, использование `userRepository` внутри `.client`-колбэка — safe boundary (не флагуется), а имя `getCurrentUserUseCase`, импортируемое и вызываемое в хуке, **не флагуется** (агент доказал построчно по `analysis.js:313-321, 399, 419-435`). Значит, перенос wiring в composition root структурно работает.

Решения пользователя:
- Все 3 use case переносятся в composition root (включая серверный).
- Server-ветки клиентских isomorphic use case — throwing-стабы.

## Изменения (4 файла)

### 1. `apps/web/src/app/composition-root/index.client.ts` — переписать
Оставить `userRepository` как есть. Экспортировать два клиентских use case как **isomorphic fns** с throwing-стабами в server-ветке:

```ts
export const getCurrentUserUseCase: () => GetCurrentUserUseCaseShape =
  createIsomorphicFn()
    .client(() => new GetCurrentUserUseCase(userRepository))
    .server(() => ({
      execute: () => { throw new Error('GetCurrentUserUseCase is client-only (LocalStorage-backed).') },
    }))

export const toggleFavoriteProductUseCase: () => ToggleFavoriteUseCaseShape =
  createIsomorphicFn()
    .client(() => new ToggleFavoriteProductUseCase(userRepository))
    .server(() => ({
      execute: () => { throw new Error('ToggleFavoriteProductUseCase is client-only (LocalStorage-backed).') },
    }))
```

Тонкость типов: терминальный тип цепочки — `IsomorphicFn<TArgs, TServer, TClient>`, т.е. функция `() => TServer | TClient`. Аннотация должна быть `() => <тип use case>` (или общий структурный интерфейс, совпадающий для real impl и throwing-стаба). Объявлю 2 структурных интерфейса (`GetCurrentUserUseCaseShape`, `ToggleFavoriteUseCaseShape`), описывающих только `execute(...)`, чтобы и реальный класс, и стаб-объект им присваивались. **Не** использую `IsomorphicFn<...>` в аннотации (это приводило к ошибкам) — аннотирую как обычную функцию `() => Shape` и проверяю `tsc`.

## Проверка (после каждой правки — `tsc`, в конце — dev-сервер)

1. `npx tsc --noEmit -p apps/web/tsconfig.json` — 0 ошибок. Если аннотации типов isomorphic fns не выводятся — итеративно поправлю (возможно, уйдёт совсем от явной аннотации и положусь на inference, раз порядок не важен).
2. Dev-сервер: `curl http://localhost:3000/catalog` → HTTP 200, и **отсутствие** `[import-protection]` и `Error in render` в логах (проверяю grep-ом по stdout/stderr).
3. Проверяю рендер: наличие «Каталог», списка товаров (не «Товаров пока нет») — значит серверный use case и SSR клиентского хука оба работают.

## Риски и митигация
- **Типы isomorphic fns** — главная зона неопределённости (я тут ошибался). Митигация: начну с inference без аннотаций, добавлю структурные интерфейсы только если `tsc` потребует.
- **Забытый импорт** в хуке после удаления wiring — `tsc` поймает.
- **Регрессия warning** — если вернётся, верну точечный `createIsomorphicFn` в хук (но по исследованию не должно).

Весь рефакторинг — 5 файлов, ~60 строк нетто-изменений, ни одной новой абстракции (только перераспределение wiring).
